# PLAYCE統合アプリ 開発準備仕様書（暫定統合版）
作成日：2026-11-03
状態：仕様方針113項目決定。既存アプリの実装・DB・認証・連携APIは未確認。

## 1. 目的と公開範囲
PLAYCEのスポーツイベント公開カレンダー、ニックネームでの申込、当日受付、会計、在庫、参加者連絡、運営分析を一元化する。参加者はログイン不要で公開情報を閲覧・申込可能。主催者専用機能はGoogleログインに加えてサーバー側で許可アカウントを検証する。参加者氏名一覧・メッセージ・会計・内部分析は公開しない。

## 2. 第1段階（MVP・最優先）
- 既存会計アプリの構造・データ・認証・保存先を調査し、完全バックアップと復元テストを行う。
- 公開カレンダー（月表示／一覧切替）、個別イベントURL、詳細（日時、場所、料金、人数、持ち物、注意事項）。
- ニックネームだけで参加申込。代表者による複数人申込、専用管理URL、同一ブラウザでの申込確認・編集・キャンセル。イベント開始まで変更可能。
- 申込時の重要ルール同意、ブラウザ識別による重複警告。ブラウザIDを確実な本人識別として扱わない。
- 定員は原則なし、イベント別に設定可。満員時はキャンセル待ちと順番繰上げ・本人の参加意思確認。通常24時間、開催24時間以内は最大6時間、開催6時間以内は最大1時間で回答期限を切り、開始時刻を超えない。
- 主催者のイベント作成・変更・複製・定期開催、公開／非表示／中止／延期、変更履歴。延期時は既存申込を維持して参加継続意思を確認。中止時は募集終了し履歴保存。
- 当日専用受付画面。ニックネーム部分一致検索、個人別受付、個人別／まとめ支払い、飛び入り追加、個別料金変更、取り消しと監査履歴。
- 申込・出欠・入金・経費をイベントと会計へ連携。予定額と入金実績を分け、同じ取引を二重計上しない。イベント終了後の会計確定と修正履歴。
- 申込者一覧CSV、受付チェック欄付き印刷用PDFは主催者のみ出力可能。個別管理URL・秘密情報は出力しない。
- 通信断でも読み込み済み一覧で受付・支払いを一時記録し、復旧後に同期。競合時は保留して主催者が判断。未同期件数を表示。

## 3. 第2段階（運営効率化）
- 変更・中止のお知らせ、任意通知、前日19時／当日12時のリマインダー。メール・対応端末へのWebプッシュは任意同意を前提とし、対応環境を検証する。
- 参加者と主催者の個別メッセージ（終了後も利用可）、写真添付、未読件数、未対応／対応中／対応完了、返信通知。
- 開催前の競技別準備チェックリスト（期限・通知）、終了後片付けリスト、運営記録と次回準備への候補引継ぎ。
- 備品の在庫・使用数・貸出返却・破損紛失・修理／買い替え、状態は「使用可能／使用不可」の2区分。未返却警告。
- 忘れ物の写真・保管状況、公開許可した一覧、受取申請と主催者承認、受渡日時調整、保管期限の主催者通知。自動処分しない。
- レシート写真／PDFとAI読み取り。商品・数量・金額の照合は人が確認してから会計・在庫に反映。購入リスト・予算管理。
- イベント写真の保存、同意に応じた選択公開、SNS用画像、案内文生成と手動投稿。

## 4. 第3段階（分析・予測）
- 参加者の初回／リピート、参加率、無断欠席、アンケート、曜日・会場・競技別の比較表とグラフ。
- 参加人数の予測は1日1回更新、更新日時と根拠を表示。主催者のホームとイベント詳細だけに表示。予測人数と申込人数・実参加人数を分ける。
- 予測人数から売上・利益を試算。予測と実績を比較し、赤字警告・改善提案・複数シナリオ保存と比較。
- シミュレーションの正式設定への反映は変更前後の差分確認・明示承認・変更履歴を必須とする。仮の値を実績会計に混ぜない。
- 在庫使用実績と今後の開催から購入必要量・時期を予測。予測値は参考情報とする。

## 5. 料金・通知の確定事項（仕様108・109）
- イベント料金変更後も既存申込者の料金は原則申込時の旧料金を維持。変更後の新規申込者には新料金を適用。
- 主催者は例外的に個別料金を変更可能。理由・変更履歴を保存する。
- イベントページに変更履歴を表示。通知希望者へ変更を知らせ、個別適用料金を案内。申込管理画面では本人の適用料金を常時確認可能。

## 6. リリース・運用（仕様110〜113）
110：基本機能から段階的に開発する。
111：旧会計アプリと並行テストし、整合性を確認してから切替。会計データの正本を一つに決め、二重入力を防ぐ。
112：主催者と少人数の参加者による実機テストに加え、自動テスト・権限／セキュリティ確認を実施する。
113：更新はテスト環境で確認し、重要な更新前にバックアップを取って本番反映する。旧版へのワンクリック復元は確定仕様ではない。

## 7. 非機能要件・実装上の重要事項
- 管理者限定データはフロントエンドで隠すだけでなく、サーバー／DBルールでアクセス制御する。
- 公開申込の不正利用対策、個別管理URLの推測防止、添付ファイルの安全な保存・閲覧権限・容量制限を設ける。
- 入出金、受付、在庫移動、キャンセル待ち昇格はトランザクション／冪等性キー等で競合・二重実行を防ぐ。
- 日次バックアップと手動エクスポート、復元手順の検証。個人情報・通知同意・写真公開同意は目的別に管理する。
- iPhoneでの操作性を優先し、PCでも管理できるレスポンシブWeb UIとする。
- LINEオープンチャットへの直接自動投稿は実現可否未確認。初期は案内文・画像生成と手動共有を採用する。

## 8. 開発着手前に必須の調査
1. 既存会計アプリのコード、使用技術、ホスティング、データベース、認証、管理権限を実物で確認。
2. 既存データの件数・構造・エクスポート可否とバックアップ／復元方法を確認。
3. 公開サイトと主催者画面のドメイン／URL、認証許可アカウント、DBアクセス制御を確定。
4. 既存会計への直接拡張か別アプリ統合か、調査結果から決定。
5. 段階ごとの受入基準とテストケースを作成。

## 9. 第1段階の最低受入テスト
- 未ログイン者が主催者会計・参加者一覧・個別メッセージを取得できない。
- 1人／複数人申込、人数カウント、編集、キャンセル、満員／キャンセル待ちが正しく動く。
- 受付済みと支払済みを独立して変更・取り消しでき、会計に二重計上されない。
- 既存会計データが移行前後で欠落・重複しない。
- 通信断での受付と復旧同期、競合保留が動作する。
- CSV/PDF出力に他人の個別管理URL等が含まれない。
- iPhone実機で主要操作を完了できる。
