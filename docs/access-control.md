# アクセス制御設計案(第1段階)

状態: 2026-11-04 ユーザー承認（案どおり）。

## 役割
| 役割 | 認証 | できること |
|---|---|---|
| 参加者(公開) | なし | 公開イベントの閲覧、自分の申込の作成・確認・編集・キャンセル(管理URLを知っている場合のみ) |
| 主催者 | Googleログイン + サーバー側の許可リスト検証 | 管理画面のすべて |

## 基本方針
- Firestore / Storage の rules は、既定をすべて拒否にする。
- 参加者の読み書きは、クライアントから直接行わせない。Next.js のサーバー側(Server Actions / API Routes)が検証して、Admin SDK で処理する。
- 主催者の判定は、Googleログインだけで済ませない。サーバーが ID トークンを検証し、許可リスト(メール、確認済みのもの)に含まれるか確認する。許可リストはコードに書かず、サーバー側の設定または専用コレクション(クライアントから読み書き不可)に置く。
- 個別管理URLは、推測できない十分に長いランダムトークンにする。DBにはトークンそのものではなくハッシュを保存する。
- 申込のブラウザ識別は重複警告にのみ使い、認可には使わない。

## コレクション別の権限
| コレクション | 公開の読み取り | 公開の書き込み | 主催者 |
|---|---|---|---|
| events(公開フィールドのみ) | 公開イベントのみ読み取り可 | 不可 | 読み書き |
| registrations(申込) | 不可(サーバー経由で、管理URL保持者の自分の分のみ) | 不可(サーバー経由のみ) | 読み書き |
| attendance / payments(受付・入金) | 不可 | 不可 | 読み書き(取り消しは履歴を残す) |
| accounting(売上・経費) | 不可 | 不可 | 読み書き |
| audit_logs(変更履歴) | 不可 | 不可 | 追記のみ(変更・削除不可) |
| admin_allowlist | 不可 | 不可 | サーバーのみ |

公開イベントの表示には、参加者氏名・メッセージ・会計・内部分析を含めない。申込者数など公開してよい集計値は、別フィールドにする。

## 公開申込の不正利用対策(案)
- 実装済み: IP別の回数制限（申込5回/10分、管理URL操作30回/10分、ログイン10回/10分）。記録に失敗したときは許可する（可用性優先）。
- 実装済み: 隠し欄と、署名つき描画時刻トークン（入力が3秒未満、または2時間超は拒否）。
- 未実装: Firebase App Check または reCAPTCHA 系。導入サービスは公式情報を確認して選ぶ。
- 要確認: 本番の X-Forwarded-For の段数（`TRUSTED_PROXY_HOPS`）。誤ると全員が同じIP扱い、または偽装可能になる。
- ニックネーム・人数・備考の入力長と形式をサーバー側で検証する。

## 競合・二重実行の防止
- 申込の人数カウント、キャンセル待ち昇格、受付、入金、在庫移動は、Firestore のトランザクションで処理する。
- 入金・経費の登録は冪等性キーを持たせ、同じ取引を二重に計上しない。
