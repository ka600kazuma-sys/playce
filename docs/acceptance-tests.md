# 第1段階 受入基準とテストケース

`docs/spec.md` §2・§9 に基づく。既存会計データの移行・並行テストは対象外(方針変更 2026-11-04)。
「自動」は `tests/` で自動化する。「実機」は人が確認する。

## A. 権限・情報漏えい
| ID | 確認内容 | 方法 |
|---|---|---|
| A1 | 未ログインで会計・参加者一覧・個別メッセージを取得できない(API、画面、rules) | 自動 |
| A2 | Googleログインしても、許可リスト外のアカウントは管理機能を使えない | 自動 |
| A3 | 他人の申込を、ID直指定・管理URL推測で閲覧・変更・キャンセルできない | 自動 |
| A4 | 公開イベントのレスポンスに、参加者氏名・会計・管理URLが含まれない | 自動 |
| A5 | 管理者API・rules が、フロントを経由せず直接呼んでも拒否する | 自動 |
| A6 | ログアウト・セッション失効後は管理操作ができない | 自動 |

## B. 申込
| ID | 確認内容 | 方法 |
|---|---|---|
| B1 | ニックネームだけで1人申込できる | 自動 |
| B2 | 代表者が複数人を申込でき、人数が正しくカウントされる | 自動 |
| B3 | 管理URL・同一ブラウザで、確認・編集・キャンセルができる。開始後は不可 | 自動 |
| B4 | 重要ルールへの同意がないと申込できない | 自動 |
| B5 | 重複の疑いで警告を出すが、本人確認の根拠にはしない | 自動 |
| B6 | 満員でキャンセル待ちになり、キャンセルで順番に繰り上がり、本人の意思確認が出る | 自動 |
| B7 | 回答期限(通常24h、24h以内は最大6h、6h以内は最大1h、開始時刻を超えない)が正しい | 自動 |
| B8 | 同時申込・同時キャンセルで、人数が狂わない(二重繰り上げなし) | 自動 |
| B9 | 入力長・形式の不正、連続申込が拒否される | 自動 |

## C. イベント管理
| ID | 確認内容 | 方法 |
|---|---|---|
| C1 | 作成・変更・複製・定期開催ができ、変更履歴が残る | 自動 |
| C2 | 公開/非表示/中止/延期が動く。中止は募集終了、延期は既存申込を維持して継続意思を確認 | 自動 |
| C3 | 料金変更後も既存申込者は旧料金、新規は新料金。個別変更は理由と履歴を保存 | 自動 |

## D. 当日受付・会計
| ID | 確認内容 | 方法 |
|---|---|---|
| D1 | ニックネームの部分一致検索で受付できる | 自動 |
| D2 | 受付済みと支払済みを独立して変更・取り消しでき、監査履歴が残る | 自動 |
| D3 | 個別/まとめ支払い、飛び入り追加、個別料金変更ができる | 自動 |
| D4 | 同じ入金・経費を二重に計上しない(冪等性キー、再送、二重タップ) | 自動 |
| D5 | 予定額と入金実績が分かれている | 自動 |
| D6 | イベント終了後の会計確定と修正履歴 | 自動 |

|---|---|---|

|---|---|---|

## 公開前の条件
- A〜F の自動テストがすべて成功する(`test.todo` が残っていない)。
- G の実機確認が完了している。
- `scripts/security-check.sh` が成功し、High/Critical の未対応脆弱性がない。
- 公開前に、使用技術の公式セキュリティ情報を再確認し、`docs/security-review.md` に追記する。
